01 · Visão geral

Modelo cliente-servidor — frontend stateless, backend faz o trabalho pesado

O frontend não decodifica nada nem aplica lógica de negócio. Todos os códigos da RF (situação, qualificação, identificador de sócio, faixa etária) chegam já traduzidos como texto. A separação Ativos/Ex-sócios e o histórico de qualificações também são responsabilidade do backend.

Frontend
Envia GET /api/v1/empresa/47819002000170 — só o CNPJ raw (14 dígitos numéricos).
Backend
Faz join de empresa + estabelecimento (matriz) + simples + socios, resolve códigos via cache em memória (qualificacao, cnae, municipio, natureza, motivo), separa sócios por dt_ultima_atualizacao contra mes_atual, monta histórico de qualificações.
Resposta
Devolve um único JSON com a estrutura completa — sem que o frontend faça nenhum lookup adicional. ~1 round-trip por tela de empresa.
Princípio: tudo que é decodificação de código da RF acontece no crud.py com cache em memória das tabelas de domínio. O frontend recebe apenas strings legíveis. Isso é o que o seu README descreve em "Decisões do site 1.0" — manter.

04 · Mapeamento campo-a-campo

Para cada campo do JSON, de onde sai no schema

O backend já tem os models corretos (backend/models.py). Esta tabela é o guia para o crud.py montar a resposta.

Campo da resposta Origem no schema Tratamento
razao_social empresa.nm_razaosocial Direto.
natureza_juridica empresa.cd_naturezajuridica Join com tabela natureza (cache em memória). Formato "205-4 — Sociedade Anônima Fechada".
qualificacao_responsavel empresa.cd_qualificacaoresponsavel Join com qualificacao (cache). Mesmo formato "código — descrição".
capital_social empresa.vl_capitalsocial Numérico em reais. Frontend formata para BRL.
porte empresa.cd_porteempresa Mapa fixo no backend: 00→"Não informado", 01→"Micro Empresa", 03→"EPP", 05→"Demais".
situacao estabelecimento.cd_situacaocadastral Mapa fixo: 01→"Nula", 02→"Ativa", 03→"Suspensa", 04→"Inapta", 08→"Baixada". Sempre da matriz (cnpj_ordem='0001').
motivo_situacao estabelecimento.cd_motivosituacaocadastral Join com motivo (cache). null se situação = Ativa.
situacao_especial / data estabelecimento.nm_situacaoespecial
estabelecimento.dt_datasituacaoespecial		 Texto livre. Trim. null se vazio. Sempre da matriz.
cnae_principal estabelecimento.cd_cnaefiscalprincipal Join com cnae (cache). Objeto {codigo, descricao}.
cnae_secundarios estabelecimento.cd_cnaesecundario String CSV. split(',') + lookup cada um → array de {codigo, descricao}.
endereco.municipio estabelecimento.cd_municipio Join com municipio (cache). UF vem direto de estabelecimento.uf.
simples.opcao_simples simples.opcao_pelo_simples Converte 'S'/'N'/null → true/false/null.
dt_primeira_carga empresa.dt_primeira_carga Já no formato YYYY-MM. Direto.
dt_ultima_atualizacao empresa.dt_ultima_atualizacao Direto.
ativo_na_base_atual derivado empresa.dt_ultima_atualizacao == mes_atual
has_filial_ativa derivado Só preencher se situacao = "Baixada". Query: EXISTS filial mesma cd_cnpjbasico com cd_situacaocadastral = 02.
socios_ativos socios Ver §05. Sócios com dt_ultima_atualizacao = mes_atual.
socios_inativos socios Ver §05. Sócios com dt_ultima_atualizacao < mes_atual.
05 · Lógica

Como separar Sócios Ativos de Ex-Sócios

Esta é a feature mais importante do produto. O crud.py já tem boa parte da lógica (sócios_ativos/socios_inativos). A diferença na v2 é que cada item carrega o histórico de qualificações dentro.

Algoritmo

# 1. Carrega todos os registros de socios do CNPJ básico
rows = db.query(Socio).filter(Socio.cd_cnpjbasico == cnpj_basico).all()

# 2. Agrupa por (cpf_cnpj_socio, identificador_socio)
#    — uma "pessoa" pode ter múltiplos registros se mudou de qualificação
grouped = defaultdict(list)
for r in rows:
    key = (r.cd_cpfcnpjsocio or r.nm_socio, r.cd_identificadorsocio)
    grouped[key].append(r)

# 3. Para cada pessoa, monta SocioWithHistory
ativos, inativos = [], []
for key, registros in grouped.items():
    # Sort: mais recente primeiro (por dt_ultima_atualizacao DESC, dt_primeira_carga DESC)
    registros.sort(key=lambda r: (r.dt_ultima_atualizacao, r.dt_primeira_carga), reverse=True)

    most_recent = registros[0]
    is_active = most_recent.dt_ultima_atualizacao == mes_atual

    socio = {
        "identificador_socio": TIPO_SOCIO_MAP[most_recent.cd_identificadorsocio],
        "cpf_cnpj_socio": most_recent.cd_cpfcnpjsocio,
        "nome_socio": most_recent.nm_socio,
        "data_entrada": min(r.dt_dataentradasociedade for r in registros),
        "faixa_etaria": FAIXA_MAP.get(most_recent.cd_faixaetaria),
        "dt_primeira_carga": min(r.dt_primeira_carga for r in registros),
        "dt_ultima_atualizacao": most_recent.dt_ultima_atualizacao,
        "qualificacao_atual": {
            "codigo": most_recent.cd_qualificacaosocio,
            "descricao": qualificacao_cache[most_recent.cd_qualificacaosocio],
            "desde": most_recent.dt_dataentradasociedade,
        },
        "qualificacoes_anteriores": [
            {
                "codigo": r.cd_qualificacaosocio,
                "descricao": qualificacao_cache[r.cd_qualificacaosocio],
                "de": r.dt_dataentradasociedade,
                "ate": end_of_month(r.dt_ultima_atualizacao),
            }
            for r in registros[1:]
        ]
    }

    (ativos if is_active else inativos).append(socio)
Chave de agrupamento: (cd_cpfcnpjsocio, cd_identificadorsocio) — a mesma chave usada para detectar duplicatas. Para sócios Estrangeiros, cd_cpfcnpjsocio é vazio, então usa nome como fallback (pode gerar falsos positivos em homônimos, mas é o melhor possível com os dados da RF).
06 · Histórico de qualificações

Por que múltiplos registros geram a linha do tempo

A chave natural de sócios inclui cd_qualificacaosocio. Mudança de qualificação = saída do registro antigo + entrada do novo. Cada par conta um capítulo da história da pessoa na empresa.

Exemplo do mock: Otávio Ramalho Sampaio aparece três vezes no banco para a Marambaia. O backend deve consolidar em um único item de socios_ativos:

Registro no banco dt_primeira_carga dt_ultima_atualizacao Posição
qualif 49 (Sócio-Adm) 2023-03 2020-12 qualificacoes_anteriores[1]
qualif 22 (Sócio-Adm v2) 2023-03 2026-04 qualificacoes_anteriores[0]
qualif 05 (Administrador) 2026-05 2026-05 (= mes_atual) qualificacao_atual

A UI renderiza isso como linha do tempo expandível ao clicar no sócio. O badge "mudou" aparece quando qualificacao_atual.desde está dentro dos últimos 12 meses E qualificacoes_anteriores.length > 0.

08 · Edge cases

Três situações que o protótipo trata e o backend precisa suportar

E.01

Situação especial preenchida

Quando estabelecimento.nm_situacaoespecial (da matriz) é não-vazio, o protótipo mostra um banner vermelho no topo do header. Backend só precisa entregar situacao_especial + situacao_especial_data não nulos. Exemplos: EM RECUPERACAO JUDICIAL · EM LIQUIDACAO · EM FALENCIA.

E.02

Matriz baixada com filial ativa

Caso documentado no README (6.648 casos na base de abr/2026). Quando situacao = "Baixada" e existe pelo menos uma filial mesma cd_cnpjbasico com cd_situacaocadastral = 02, retornar has_filial_ativa: true. O frontend mostra banner amarelo de aviso.

Query:

SELECT EXISTS(
  SELECT 1 FROM estabelecimento
  WHERE cd_cnpjbasico = :basico
    AND cd_cnpjordem != '0001'
    AND cd_situacaocadastral = '02'
)
E.03

Empresa fora da base atual

Quando empresa.dt_ultima_atualizacao < mes_atual — significa que a empresa saiu da base oficial em algum mês passado. O frontend marca ativo_na_base_atual: false no card temporal lateral. Não retornar 404 — a empresa continua existindo no histórico do Pythagoras (esse é um dos diferenciais).

09 · Performance da busca por texto

Já documentado no README — só reiterar

Os endpoints /empresa/busca?nome= e /socio/busca?nome= dependem de índice trigram. O autocomplete do protótipo (4 sugestões) vai estourar latência se o índice não estiver criado.

SQLite dev
Rodar uma vez: py -3.12 backend/criar_indices.py — cria fts_empresa e fts_socio com tokenizer trigram. Tempo: 30-60 min. Disco: +20-30 GB. Sem esse passo, autocomplete leva minutos.
PostgreSQL
Ativar extensão + GIN: CREATE EXTENSION pg_trgm; CREATE INDEX idx_empresa_razao_trgm ON empresa USING GIN(nm_razaosocial gin_trgm_ops); — feito uma vez. ILIKE usa o índice automaticamente.
Crud
A função is_postgres() no database.py já decide a estratégia em runtime — não há mudança de código. O autocomplete do frontend bate em /empresa/busca?nome=X&limit=5 a partir de 3 caracteres digitados.
Detalhe importante: o autocomplete deve fazer debounce de 200-300ms no frontend antes de chamar a API. Sem isso, cada tecla dispara uma query. Isso é só ajuste no JS — não precisa mudar o endpoint.
